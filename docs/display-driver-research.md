## Инициализация дисплея

```cpp
#include "Arduino_GFX_Library.h"

// Шина QSPI — наши пины (1.32" отличаются от 1.75"!)
Arduino_DataBus *bus = new Arduino_ESP32QSPI(
    LCD_CS,   // GPIO10
    LCD_SCL,  // GPIO11
    LCD_D0,   // GPIO12
    LCD_D1,   // GPIO13
    LCD_D2,   // GPIO14
    LCD_D3    // GPIO15
);

// Дисплей CO5300
// ВАЖНО: col_offset1 = 6 — без этого картинка сдвинута!
Arduino_CO5300 *gfx = new Arduino_CO5300(
    bus,
    LCD_RESET,  // GPIO8
    0,          // rotation
    466,        // width
    466,        // height
    6,          // col_offset1 — ОБЯЗАТЕЛЬНО
    0, 0, 0     // остальные offsets = 0
);

void setup() {
    gfx->begin();
    gfx->fillScreen(RGB565_BLACK);
    gfx->setBrightness(200); // 0–255
}
```

### Что делает col_offset1 = 6
CO5300 — контроллер на 480×480, но физический дисплей 466×466. Сдвиг 6 пикселей
компенсирует разницу в адресации столбцов. Без него изображение будет смещено влево.

## LVGL — буферная стратегия

Waveshare использует **два буфера по 1/4 экрана** в DMA-памяти (внутренняя SRAM):

```cpp
// 466 * 466 / 4 = 54,289 пикселей = ~106 KB на буфер
lv_color_t *buf1 = (lv_color_t *)heap_caps_malloc(
    466 * 466 / 4 * sizeof(lv_color_t), MALLOC_CAP_DMA);
lv_color_t *buf2 = (lv_color_t *)heap_caps_malloc(
    466 * 466 / 4 * sizeof(lv_color_t), MALLOC_CAP_DMA);

lv_disp_draw_buf_init(&draw_buf, buf1, buf2, 466 * 466 / 4);
```

**Почему DMA, а не PSRAM?**
`MALLOC_CAP_DMA` выделяет из внутренней SRAM (она DMA-capable).
PSRAM медленнее для frame buffer — DMA из PSRAM добавляет латентность.
Внутренней SRAM у ESP32-S3 320 KB, из них ~212 KB свободно под буферы.

**Flush callback:**
```cpp
void my_disp_flush(lv_disp_drv_t *disp, const lv_area_t *area, lv_color_t *color_p) {
    uint32_t w = area->x2 - area->x1 + 1;
    uint32_t h = area->y2 - area->y1 + 1;
    gfx->draw16bitRGBBitmap(area->x1, area->y1, (uint16_t *)&color_p->full, w, h);
    lv_disp_flush_ready(disp);
}
```

## Решение по стеку для StarBoy

**Принято:** Arduino_GFX + LVGL 8.3.11 для UI-слоя.

**Для глазок — прямой рендер, не LVGL:**
LVGL хорош для кнопок/текста, но для плавной 30fps анимации глазок
лучше рисовать напрямую через примитивы GFX библиотеки.
LVGL оставляем для вспомогательного UI (статус Wi-Fi, заряд батареи).

**Буферная стратегия для глазок:**
- Один полный кадр 466×466×2 = 434 KB — в PSRAM (для рендера)
- DMA-буфер 1/4 экрана (~106 KB) — в SRAM (для LVGL / flush)
- FreeRTOS задача рендера на Core 1, flush на Core 0

## Рендеринг глазок — процедурный подход (не спрайты)

### Как рисуется каждый кадр

Каждые 33 мс (30 fps) FreeRTOS-задача на Core 1 вызывает `Eyes::update()`:

```
1. Стереть только bounding box глаза (fillRect ~134×134 px) — не весь экран
2. fillEllipse(cx, cy, 65, 65×irisScaleY, AMBER)   → радужка
3. fillCircle(cx+dx, cy+dy, 26×pupilScale, BLACK)   → зрачок со смещением взгляда
4. fillCircle(cx, cy−130×lidOpen, 67, BLACK)        → веко (чёрный круг сверху)
5. fillCircle(cx−20, cy−20, 5, WHITE)               → блик
```

Два глаза × 5 примитивов = 10 вызовов GFX на кадр. Каждый вызов идёт через QSPI на скорости ~40 МБ/с.

### Почему нельзя использовать спрайты

**Спрайт** — это заранее нарисованная картинка (PNG/BMP), которая хранится в памяти и просто копируется на экран. Для некоторых проектов это удобно — но не для StarBoy.

**Причина 1 — Flash слишком мал.**
8 МБ Flash делится на: загрузчик + таблица разделов + весь код прошивки. Уже сейчас код занимает 13.2%. Полный набор спрайтов для двух глаз с анимацией выглядит так:

```
6 эмоций × 10 кадров моргания × 2 глаза × 130×130 пикселей × 2 байта = ~4 МБ
```
Это половина всего Flash — для одного только набора глаз, без вариаций взгляда.

**Причина 2 — зрачок не может быть статичным.**
Зрачок постоянно двигается — за ориентацией в пространстве (через гироскоп). Для спрайтов пришлось бы хранить картинку для каждой позиции зрачка. Позиций минимум 20×20 = 400 вариантов на каждую эмоцию. С процедурным рендером это одна строка кода:
```cpp
gfx->fillCircle(cx + lookX * 18, cy + lookY * 18, pupilRadius, BLACK);
```

**Причина 3 — эмоциональные переходы.**
При смене эмоции (например, IDLE → HAPPY) глаза плавно меняются через LERP — промежуточные состояния вычисляются в реальном времени. Со спрайтами это невозможно: нет спрайта для «42% HAPPY, 58% IDLE».

**Причина 4 — моргание комбинируется с любой эмоцией.**
Моргание — это движение века. Оно должно работать поверх любой эмоции в любой момент. Со спрайтами нужно хранить `N_эмоций × N_кадров_моргания` наборов. Процедурно это один параметр `lidOpen`.

**Итог:** процедурный рендер — это рисование математикой вместо хранения картинок. Занимает ~0 Flash, бесконечно гибкий, даёт плавные переходы.
